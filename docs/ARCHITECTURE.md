# Architecture

## Why LLM consensus, not a deterministic rule

A naive provenance registry would just check: "is this wallet linked to a real
human via KYC?" But KYC has three problems onchain:

1. **It requires a trusted verifier** — exactly the thing GenLayer's consensus
   model is built to remove
2. **It can't judge qualitative claims** — "is this track AI-generated?" has
   no boolean answer
3. **It's static** — identity verification at registration doesn't catch
   disputes filed later

LLM comparative consensus handles all three:

- **No single trusted party** — the leader proposes a score, validators
  re-fetch the evidence and re-score independently. The leader's score is
  only accepted if a majority of validators land within a tolerance band
  (15 points here).
- **Qualitative judgments** — the LLM evaluates the evidence with explicit
  criteria, returning a 0-100 score that's auditable onchain
- **Repeated application** — the same pattern handles both registration and
  disputes, so a previously-verified artist can be re-judged if challenged

## Why two tolerance-band validators, not strict_eq

`gl.eq_principle.strict_eq` requires all nodes to return *exactly* the same
value. That works for fetching a block height from an API. It does NOT work
for LLM judgments, where the same prompt can return 82 on one node and 79 on
another for legitimate reasons (model temperature, context length
differences, etc.).

So we use `run_nondet_unsafe` with a custom validator that re-runs the
judgment and accepts if it lands within a 15-point band. Wider drift means
the evidence is genuinely ambiguous, and the contract should not write to
state.

## Why 70 is the threshold, 60 for disputes

**Verification threshold: 70.** A score below 70 means the evidence is too
sparse to confidently claim a real identity. Real artists with even minimal
web presence (one music platform, one social profile) should clear this.
Fabricated identities with no cross-source corroboration should not.

**Dispute uphold threshold: 60.** Lower than verification because the burden
of proof is asymmetric: a real artist should be able to register with
modest evidence, but it should be easier to challenge a release than to
defend one. 60 (vs 70) means a single piece of credible evidence (e.g., a
Clearbit audit showing a track was generated by Suno) is enough to flip
the release to contested.

**Tolerance band: 15.** A 15-point spread on a 0-100 score is wide enough
to absorb LLM variance, narrow enough that a validator wildly
over-estimating or under-estimating the leader's claim gets rejected.

These three numbers are the *only* knobs in the contract. If they're wrong,
they can be tuned in a v2 — but the shape (multi-source fetch, comparative
consensus, asymmetric burden) is the load-bearing part.

## Why "contested" is a sticky bit, not a deletion

Once a release is marked contested, it stays contested. This is intentional:
a contested release should not be cleared just because the original artist
files a counter-dispute and the LLM judge happens to score it favorably.
The reputation penalty stays. The "contested" flag stays. If a downstream
service (streaming platform, sync licensor) wants to ingest a contested
release, they can read the dispute record and decide.

The path to clearing a contested release would be an explicit
`clear_dispute(audio_hash)` method, but that's deliberately out of scope
for the MVP — too easy to abuse.

## Why we re-fetch the same evidence for every validator

A naive validator would just call the LLM with the leader's output and ask
"is this reasonable?" That's a security hole: the validator is asking the
LLM to trust the leader's framing. The LLM has no way to know if the
leader's evidence is real or fabricated.

So the validator re-fetches the URLs from scratch. This costs more
(consensus time, validator bandwidth) but it's the only way to get
non-circular validation. The leader's job is to propose; the validator's
job is to independently verify the proposal by re-running the experiment
from the same inputs.

## State

Six maps. Three are user-facing (`artists`, `releases`, `disputes`); three
are internal counters that prevent gaming:

- `identity_score` — the *last* consensus score for a wallet. A failed
  attempt still updates this so a wallet can't keep retrying with the same
  bad evidence.
- `identity_count` — how many times the wallet has tried to register.
  Useful for rate-limiting future work.
- `artist_releases` — index of audio hashes per artist. Cheap to fetch
  "all releases by artist X" without scanning the entire `releases` map.

## What this contract is NOT

- **Not a legal proof of ownership.** The onchain record is evidence, not
  a substitute for a copyright registration. A real legal dispute still
  needs a court.
- **Not a copyright enforcement system.** Filing a dispute does not delete
  the release. It marks it as contested, which downstream services can
  act on, but the contract has no view of off-chain music distribution.
- **Not a substitute for platform moderation.** A streaming platform
  should still do its own checks; this contract is one signal, not the
  only signal.
- **Not anonymous.** The `register_artist` method links a wallet to a
  real-world identity. Artists who want to remain pseudonymous can do so
  (use a stage name, link to a DID that doesn't reveal legal name), but
  the *wallet* is permanently tied to the verification evidence.
